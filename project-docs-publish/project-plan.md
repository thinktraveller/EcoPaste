## 项目概述

- 项目目标：让剪贴板窗口内的快捷键可以设置，并支持按下 `Ctrl+Shift+V` 将当时系统剪贴板中的带格式文本转换为纯文本。
- 核心成果：窗口快捷键配置入口、有效绑定在各执行路径和提示中的一致表现、当前系统剪贴板的纯文本转换能力、已发布设置数据的升级策略及 macOS / Windows 验收记录。
- 使用场景：用户根据个人习惯调整窗口操作；从网页或办公软件复制格式化内容后，主动去掉剪贴板格式。
- 已有架构：Tauri v2、Rust、React 19、Ant Design v6、UnoCSS、Valtio UI 镜像、sqlx / SQLite；业务、系统能力和持久化放 Rust。仅支持 macOS 与 Windows。
- 本轮范围：规划以上两个需求。首期采用全局只转换、原生文本优先、常用列表动作可配置；自动粘贴、HTML/RTF 解析补全和全部导航键任意改绑留作后续扩展。以下方案可按用户反馈调整。

| D4 | 窗口动作范围 | 首期开放粘贴、纯文本粘贴、复制、打开、收藏、置顶、备注、删除等常用列表动作，每动作一个绑定，可禁用、恢复默认，初始键保持当前行为 | 导航、Space 按住预览、Esc 层级关闭、Tab 和数字快速粘贴先保留默认；其改绑作为后续阶段，首期不得宣称全部键均可配置 |

| D6 | 冲突与失败 | 同作用域重复及会抢占同一动作入口的跨域组合拒绝；改绑或保存失败恢复旧配置/旧注册；恢复失败显式展示真实未生效状态 | 启动注册失败保留期望配置并报告，不误报为已生效；多键恢复不视为操作系统事务 |
| D7 | 并发与写回 | 单次在途保护、触发去重、写前状态复核，变化则取消；写失败只撤销本次 Guard 登记并报告，不盲目重试 | 不能承诺跨进程绝对原子；写入中途失败可能部分改变系统剪贴板，需实测并说明 |

## 可行性分析

- 技术可行性：主要沿用已存在的系统能力，不需要先获取另一份源码。关键工作在于把当前硬编码行为变为受控配置，以及建立不依赖历史 ID 的当前剪贴板操作。
- 第三方依赖：当前使用 `clipboard-rs`、`tauri-plugin-global-shortcut`、serde、Tauri 和现有 UI 库；本计划不批准新增依赖。若选 D3 的解析路线，再评估解析正确性、包版本和体积。
- 工作量估算：在选择原生 Text 路线、现有架构和较小首批动作范围的前提下，约 8—13 人日，包括设计/迁移 1—2、转换能力 1—2、窗口配置与两端键盘路径 3—5、回归和修正 3—4。属于规划估算，非承诺；全动作任意重绑、HTML/RTF 转换或自动粘贴会扩大工作量。
- 平台依赖：Windows 与 macOS 的真实桌面会话均必要；无 macOS 验证设备时标记 macOS 待验收，不将 Windows 通过等同于双平台通过。

| 风险 | 具体影响与应对要求 |
| --- | --- |
| 旧设置/默认值变化 | 不能仅依赖 serde(default) 宣称升级兼容；缺失新增键是否自动注册与空值是否禁用需明确迁移规则 |
| 操作系统占用组合键 | 保存成功但功能无效；注册失败必须在最终选定状态模型中可见，重启仍能解释真实状态 |
| 多修饰键丢失 | Ctrl+Shift+C 被误当成 Ctrl+C；两条事件路径都须精确匹配，额外修饰键不得自动降级 |
| 编辑态吞键 | 搜索或备注中输入、复制、方向/删除变成历史动作；必须保留编辑态和输入法合成保护 |
| 读取/写入竞态 | 用户在读取后又复制新内容，旧文本覆盖新内容；D7 需要明确检测范围及不能消除的跨进程窗口 |
| 写入失败 | 清空系统格式后写入失败可能丢失原剪贴板；不能把简单 set 调用描述为事务，也不能无条件重试覆盖更新内容 |
| 抑制登记残留 | 失败写入留下哈希，短期误吞一次真实复制；处理必须局限于本次登记，不清空其他在途写回 |
| 提示与执行漂移 | 菜单显示旧快捷键、设置显示期望值但当前注册失败；显示和执行采用已确认的一致性契约 |
| 无前端窗口时反馈 | 仅广播给隐藏/销毁 WebView 的 toast 可能没人看到；D3 中确认提示载体，不能依赖主动打开剪贴板窗口 |
| 非文本和混合格式 | 仅看 Text 是否存在可能把文件路径或图片说明变成唯一内容；先明确 D3 的类型优先级 |

## 技术选型

沿用 AGENTS.md 明确指定的 Tauri v2 + Rust、React 19 + Ant Design v6 + UnoCSS presetWind4、Valtio UI 镜像、sqlx + SQLite、Vite + pnpm。设置继续以当前 Rust SettingsStore 为事实基线；新增字段和协议按 D5/D8 细化。SQLite 当前存在，但本次需求尚未确定需要新增表或 migration；如最终设计涉及 schema，必须新增 migration，禁止改写已发布文件。

- 拟在 `src-tauri/src/clipboard/` 增加当前内容转换服务，读取、格式判定、写回和保护均在 Rust；`commands/clipboard.rs` 增加薄命令 `convert_current_clipboard_to_plain_text`，全局快捷键直接调用同一服务。
- 服务结果区分已转换、无需转换、不支持和失败；新命令在 `lib.rs` 注册，名称与新增事件在 Rust 模块常量和 `src/constants/` 同步。准确序列化结构在 Trellis 设计中固化。
- 设置模型增加全局转换绑定与窗口动作绑定；`shortcut/` 负责注册与生效状态，`keyboard/` 负责 Windows 钩子，前端现有键盘入口负责 UI 动作分发。
- 首期沿用当前依赖与锁文件，不新增格式解析库；采用 D7 的保守保护，不引入无依据的重试时限或性能承诺。
- 部署：沿用现有 macOS / Windows 桌面项目发布流程；本轮没有发布或推送授权。

## 开发计划

各步骤以 D1—D8 的推荐方案为规划基线，实施时按 Trellis 工作流形成任务与具体设计。本次不启动实现。步骤依赖为：1 → 2 → 3；2 → 4；2/3/4 → 5 → 6 → 7。优先完成转换服务及对应全局触发，再推广窗口配置；步骤 3 的全局接线可提前取自步骤 5，避免等待窗口改绑完成才验证转换路径。

### 步骤 1：确认动作范围与用户行为

来源：R001、R002、C001；方案依据：D1—D4。

#### 目标说明

确认“当前系统剪贴板转换”与“选中历史记录纯文本粘贴”是不同目标，并确定窗口改绑首期覆盖范围。

#### 具体操作

1. 从 List、Group、KeyHint、ShortcutList、Header 和菜单枚举建立现有动作清单，记录默认键、keydown/keyup、长按/松开语义、编辑态例外。
2. 按 D1—D4 建立首期范围；记录 Windows 的 Ctrl+Shift+V 与 macOS 对应键是否一致，区分只转换和转换后粘贴。
3. 确认文本、纯文本、HTML/RTF-only、图片、文件、空值及混合内容的期望结果，形成对应验收用例。

#### 验证方法

每个开放动作都能定位至少一个当前执行入口；每种剪贴板输入都有明确输出与反馈；推荐方案明确记录，不混同于用户逐项指定的需求。

#### 风险提示

Space 预览的按住/释放、Esc 分层关闭和数字快速粘贴不是简单字符串替换；首期是否纳入必须明确。

### 步骤 2：确定设置、动作与跨端契约及升级规则

来源：R001、R002、C001、C002；依赖步骤 1；方案依据：D2、D5、D6、D8。

#### 目标说明

使配置可持久化，且 Rust、前端、菜单、钩子和生效状态对同一个绑定有一致解释。

#### 具体操作

1. 按选定结构扩展 Rust `Shortcuts` 与 TS 镜像；声明动作和作用域、支持键集合、别名归一化规则、禁用与缺失字段的区别。
2. 沿用 SettingsStore 的读写边界；在更新、加载、导入与重置入口检查新约束。设置覆盖导入接入点包括 `backup/mod.rs` 调用 `replace_from_file` 的链路。
3. 定义设置保存与系统注册的失败契约：保存失败、注册失败、旧绑定恢复失败、启动冲突和录入恢复冲突均需有确定结果。
4. 形成升级前后 JSON 样例、回滚说明和未知字段政策。按 D5/D8 在实施设计中补齐字段和代码样例，再通过兼容性验证固定发布数据格式。

#### 验证方法

使用脱敏旧配置验证保留原 openClipboard、openPreference、winV；新增字段缺失、显式禁用、无效组合、重复组合、未知动作、部分 JSON patch、设置导入和重启均覆盖。确认失败时磁盘、内存和实际 OS 注册状态可解释。

#### 风险提示

当前 `serde(default)` 能补字段，但不能替代产品迁移政策；现有 normalization 未统一修饰键顺序及 Ctrl/Control 等别名。

### 步骤 3：实现当前系统剪贴板转换能力

来源：R002、C001；依赖步骤 2；方案依据：D1、D3、D5、D7。

#### 目标说明

在触发时读取当前系统内容并按选定边界转换，避免误用历史选择项和采集设置。

#### 具体操作

1. 在 Rust 剪贴板业务层实现已确认的读取、判定、写回流程；入口协议与模块位置按 D5 和技术选型细化，命令层仍只校验与转发。
2. 审核 `ClipboardReader` 与写回函数的可提取范围；不要为调用历史命令而先伪造/写入一条历史记录。若采用原生 Text 路线，缺少 Text 时不能回退为 HTML/RTF 源码字符串。
3. 复用仅 Text 写入方式，保持 `ClipboardContext` 在同步段内构造和使用，不能跨 await 保存 `!Send` 句柄。以下只是现有写回模式示意，尚未包含新动作的竞态和失败补偿：

   ```rust
   // 现有 write.rs 的错误传播和仅 Text 写回方式；text 必须来自已确认来源。
   ctx.set(vec![ClipboardContent::Text(text)])
       .map_err(|err| AppError::Clipboard(err.to_string()))?;
   ```

4. 按 D7 实现同动作在途保护、触发去重、读写前状态复核和失败处理；复用内容哈希及 Guard，失败只清理本次登记，不能移除其他写回。
5. 按本版 D1-A，不调用历史 ID 命令、不更新历史使用时间/次数、不调用 simulate_paste、不打开或隐藏窗口。其它 D1 选择须补充对应焦点和注入设计后执行。

#### 验证方法

网页/办公软件复制的 Text+HTML、Text+RTF 转换后粘贴为纯文本；同时检查系统格式而非只看粘贴外观。历史选中项不同、监听暂停、采集 Text 关闭、来源应用被过滤时分别验证所选语义。注入读取失败、写入失败、并发复制和重复触发，确认失败不是“空文本成功”。

#### 风险提示

系统 set 可能先清空再写，失败不能保证原格式仍在；Guard 只抑制回环，不是互斥锁。状态复核与写入之间仍可能发生外部复制，必须记录实际保证范围。

### 步骤 4：改造窗口快捷键执行与 Windows 钩子

来源：R001、C001；依赖步骤 2；方案依据：D4、D5、D6、D7。

#### 目标说明

用户修改后在 macOS 浏览器事件和 Windows 不聚焦窗口路径均生效，原来硬编码快捷键不再抢占新绑定。

#### 具体操作

1. 按确定的动作契约调整 List、Group 和 KeyHint 等执行入口；共享既有业务动作，保留适用内容检查、删除确认和分层关闭等行为。
2. 扩展 `useKeyboardEvent` 与 Rust keyboard://nav 的契约，完整表达所选键及 Ctrl / Shift / Alt / Meta；确切 payload 字段由 D5 确认并双端同步。
3. 改造 Windows 固定白名单，依据有效配置匹配并吞键；配对处理 keydown/keyup，区分允许重复导航与禁止重复副作用。
4. 保留输入控件、contenteditable、选中文本复制、输入法合成和弹窗录入的原生行为；窗口隐藏、导航停用时不能继续吞窗口快捷键。

#### 验证方法

重绑复制/纯文本粘贴等首批动作，新键生效、旧键不触发旧动作；额外修饰键不误匹配；禁用后无动作。分别走真实 macOS 事件、Windows 不聚焦钩子与编辑态浏览器路径，确认一次物理按键只执行一次。

#### 风险提示

钩子决定吞键时还未得到前端异步回执，不能设计成“发给前端再看是否 preventDefault”才决定系统是否收到键；需要事先一致的生效配置。

### 步骤 5：扩展设置录入、全局触发与全部提示入口

#### 风险提示

### 步骤 8：完善右上角窗口置顶悬挂交互

来源：R003（2026-10-02 用户“剪切板右上角增加‘置顶’悬挂选项”）、C001、C002。既有 Header 固定按钮、Rust 固定状态与平台窗口层级为现状依据。

#### 目标说明

让用户在剪贴板右上角明确开启与关闭窗口悬挂；与历史记录的“置顶排序”区分。右上角已存在固定窗口按钮，窗口也已配置顶层显示，因此开发应从现有交互和实际平台行为出发，避免重复增加功能入口。

#### 具体操作

1. 将窗口悬挂的最终行为落到已确认的用户选择；`⏳ 待用户决策`：是否同时保持展开、关闭后如何恢复自动隐藏，以及重启是否保留。参考是“窗口保持最上层，固定后不因失焦自动隐藏；再次点击恢复”，利用现有固定态；该参考尚未作为已确认行为写入设计。
2. 核对 `Header.tsx` 的现有按钮、tooltip、激活样式及快捷键。面向用户的“置顶/取消置顶”文案与状态应清楚表达窗口行为，补齐 zh-CN / en-US。具体按钮形态、是否保留现有快捷键由实施设计确定：`⏳ 待用户决策`。
3. Rust 仍负责窗口事实状态，前端只做展示与交互。现状是 Header 本地 `useState(false)` 与 Rust 进程 AtomicBool；重新挂载可能与 Rust 状态不一致，需在确认状态契约后处理初始化和同步。新增状态接口、事件、字段名称与是否持久化：`⏳ 待用户决策`。若持久化，须明确旧配置缺失字段的升级行为，不能无依据修改已发布默认契约。
4. 在 Windows 核对 `alwaysOnTop: true`、外部点击钩子与非聚焦导航；在 macOS 核对 NSPanel Dock 层级、resign-key 自动隐藏和固定态粘贴焦点交接。当前 pinned 与临时 auto-hide suspended 共同控制失焦隐藏；不能把用户悬挂状态与文件选择的临时暂停互相覆盖。
5. 按确认后的关闭语义，核对 Esc、关闭按钮、全局窗口 toggle、复制后隐藏及粘贴后焦点；显式关闭与失焦自动隐藏应分别定义。具体平台层级调整方案：`⏳ 待用户决策`，不把原生顶层 API 的调用视为已确定改动。

#### 验证方法

两平台实际点击右上角控件，检查激活文案和样式；点击其它应用、切换应用、复制与粘贴历史项时验证确认后的悬挂行为。取消悬挂、手动关闭、快捷键开关、搜索输入和原生文件选择结束后核对状态。重挂载及重启按确定政策验证，不出现 UI 显示已关闭而 Rust 仍阻止隐藏。历史记录置顶排序和收藏不受窗口按钮影响。

#### 风险提示

当前窗口已经置于高层级，另加 z-order 开关可能改变未悬挂状态的既有展示；macOS 固定态粘贴需要让出并恢复 key window，不能改成一直抢焦点。Windows 固定后窗口导航钩子仍活跃，应实际检查用户在其它应用输入时不会误消费按键。顶层显示不等于能够覆盖系统安全界面或所有其它顶层窗口，不追加这种承诺。

### 步骤 9：修正当前系统剪贴板的标记转纯文本语义

来源：R005（2026-10-02 用户明确“将各种标记语言，如 Markdown、HTML，转换为不带标记的纯文本”）、R002、C001；依赖本轮审计与下方待决策项。

#### 目标说明

在已存在的当前剪贴板转换服务中实现用户明确要求的 Markdown / HTML 标记去除。当前服务仅移除剪贴板的富格式载荷，没有标记解析，不能视为本需求已完成。

#### 具体操作

1. 延续现有 `clipboard/plain_text.rs` 服务和薄 command / 全局快捷键入口，读取触发当时系统内容，不通过历史记录 ID 获取待转换文本。确认 Text-only Markdown、Text-only HTML、HTML-only 和原生 Text + HTML 的处理契约；Markdown / HTML 覆盖范围已由用户明确，无需再次确认是否支持它们。
2. 算法、Rust 解析库、最低版本、Markdown 方言与识别优先级：`⏳ 待用户决策`。参考路线是在 Rust 使用结构化解析，区别标记节点与正文，HTML 正文提取时处理实体、段落、换行并排除 script/style；Markdown 处理标题、强调、链接、列表和代码围栏。参考不等于已批准新增依赖或确定库名。简单正则去符号会误删正文中的星号、尖括号和代码，不能据此宣称通用解析完成。
3. 链接目标是否保留、图片替代文本、表格列分隔、代码块正文、转义符、空白和换行归一规则：`⏳ 待用户决策`。参考保留可读正文和代码内容、去除外围标记；列表层次、链接 URL 和表格不能在没有确认时静默丢失。普通纯文本与比较表达式不得因格式识别过宽被无依据改写。
4. RTF 的原生 Text 去富格式是已有兼容路径，应回归保留；RTF-only 解析及“各种标记语言”中 Markdown / HTML 之外的名单：`⏳ 待用户决策`。不能把图片、文件或不支持格式写成空文本。HTML-only 已属于用户明确的 HTML 转换范围，当前 Unsupported 分支需要相应调整。
5. 保留在途互斥、代次复核、快照比对、精确撤销 Guard 和只写 Text 的现有保护；解析放在写回前，复核覆盖新增解析耗时。Guard 哈希必须登记最终输出而非原标记源码，并继续对齐 ingest 的 trim 规则。错误或转换期间新复制到达时保持取消/失败结果，不盲目重试恢复旧内容。
6. 转换状态与序列化结构沿用现有结果枚举作为事实基线；如需扩展，准确字段/状态契约：`⏳ 待用户决策`。判断“成功”必须以实际完成纯文本写回为依据，不能仅以尝试解析或按键触发作为成功。

#### 验证方法

用下方最小例子验证内容，并逐一核对剪贴板实际剩余格式。按确认后的方言覆盖嵌套强调、引用/列表、转义符、链接、代码围栏、表格、HTML 实体、br/段落、script/style、畸形输入与中英/emoji。覆盖纯文本、空内容、HTML-only、Text+HTML、Text+RTF、图片/文件混合、读取失败、写入失败、两入口并发、解析期间外部复制与长按；确认不新增历史使用次数、不模拟粘贴。

#### 风险提示

剪贴板 Text-only 本身没有可靠的 Markdown 类型标签，弱语法可能与普通文本重合；覆盖更多方言需要明确识别策略。HTML 正文提取不能运行脚本、加载资源或简单拼接所有节点。解析结束后的代次复核仍不能与外部复制形成跨进程原子事务，系统清空后写入失败也仍可能部分改变剪贴板。

## Q&A 记录

### 步骤 3：当前系统剪贴板转换

**Q：** 现有纯文本粘贴能否直接复用？

**A：** 可以复用底层仅 Text 写回和 Guard 思路。公开的 `write_to_clipboard`、`paste_clipboard_item` 均需要历史 ID，且有历史使用信息、窗口显隐或模拟粘贴副作用，不能原样作为当前剪贴板转换入口。原生 Text 缺失时，历史 content 回退不是可靠的 HTML/RTF 转纯文本算法。

### 步骤 4：窗口快捷键配置

**Q：** 能否只把前端判断中的按键改成设置值？

**A：** 不够。Windows 不聚焦窗口依赖 Rust 固定白名单；菜单、速查和 KeyHint 也持有按键知识。执行路径、修饰键传输、吞键配对及提示必须一起核对。

### 步骤 5：设置与生效状态

**Q：** 设置保存成功能否表示新全局键已经可用？

**A：** 当前不能。`update_settings` 先保存，`shortcut::apply` 对单个注册失败只记录日志/发事件，整体继续返回成功。新设计必须按 D6 明确失败状态，不把已保存文案当作 OS 注册成功证明。

### 通用问题

**Q：** 本地是否仍只有安装文件，必须先取得官方源码？

**A：** 否。当前工作区已有完整前后端源码和 Git 历史，本计划基于主仓库 `f297878` 核查；原会话安装目录结论仅作历史上下文。

**Q：** 本轮是否已经批准“只转换不粘贴”及全部技术实现？

**A：** 用户明确要求的是可配置窗口快捷键和 Ctrl+Shift+V 转换当时系统剪贴板。只转换不粘贴、全局作用域、首期格式限制与具体动作配置模型是参考方案，见 D1—D8，本版采用其推荐方案开展规划，仍可按用户反馈调整。

条件估算：如选择复用现有窗口固定入口、覆盖常见 Markdown / HTML 并采用短暂不抢焦点反馈，约 4—7 人日，含语义/依赖设计、实现和双平台回归。该估算针对参考方案，不构成用户已经选择它或工期承诺；完整多方言、RTF-only 或新持久化契约会扩大工作量。

沿用项目指定技术栈和已锁定依赖，不执行安装或升级。当前声明下限为 `node >= 20.0`、`pnpm >= 10.0`、`Tauri >= 2.0`、`React >= 19.0`、`Ant Design >= 6.0`；Node 24 与 Rust 1.96.0 是现有 CI / 历史验证工具链基线，不能据此虚构 Rust 最低支持版本。新增解析库及其最低版本：`⏳ 待用户决策`，选择后补齐安装与兼容性说明。

本轮读取了现有 `_verify/clipboard-conversion` 的构建脚本和用例：其测试包括原生 Text 精确保留、HTML-only 不写、图片/文件保护、读写失败、竞态、Guard 撤销和重入。测试没有覆盖标记解析，本轮未执行这些测试，不据历史通过结果声称新增语义已验收。此前 buildlog 与 task 记录 Windows EXE 已构建覆盖，现有 task 的完整 Windows 功能矩阵和 macOS 验收仍未完成；本轮不改写这些记录。

以下均为待决策位置，括号中的倾向性参考不代表默认实施。

### 本轮重要 Q&A

**Q：** 目前 Ctrl+Shift+V 转换是否真的把 Markdown / HTML 标记去掉了？

**A：** 没有。服务要求原生 Text 与 HTML/RTF payload 同时存在，再将原生 Text 原样写回；Text-only 标记源码被判为无需转换，HTML-only 被判为不支持。已有逻辑能清除系统富格式，但没有标记解析。步骤 9 以本轮明确语义修正，优先于旧 D3 首期限制。

**Q：** 为什么增加“已经转换格式”不能只改前端命令包装？

**A：** 全局快捷键直接在 Rust 调用转换服务，成功状态现在没有反馈。提示必须覆盖该真实入口，隐藏窗口时也需要用户看得到；只有实际成功写回才能使用该文案，不能把 Unchanged / Unsupported / Changed / Busy 当作成功。

**Q：** 右上角“置顶”与历史记录“置顶”是什么关系？

**A：** 用户本轮描述指向窗口悬挂入口；历史记录置顶只改变列表排序。窗口已有固定按钮和原生高层级，现有固定态控制失焦及复制/粘贴后是否保持可见，最终展示行为仍按窗口问题的用户答复确定。

**Q：** 本轮是否已经实施这两个功能并修复转换？

**A：** 本轮按用户调用的规划代理交付代码审计和增量步骤；没有业务代码修改、Trellis 任务创建、运行验收或 EXE 覆盖。后续由 project-builder-cn 在待决策项确认及 Trellis 规划审阅后执行，不能用规划文档提交代替功能完成。
